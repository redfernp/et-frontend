# Local dated daily-tips import contract — 13 October 2026

This is an offline intake prototype for the existing daily processing tool. It does **not** publish to WordPress, Cloudflare, or the live site. The exact Dark Horse/Kempton pages remain noindex previews and show feed-unavailable by default.

## Inputs

The tool must export one UTF-8 CSV with this exact header and order:

`Time,Course,Horse Name,Forecast SP,Jockey,Trainer,Tissue Value Price`

Alongside it, the tool must generate a manifest at the time it prepares the selections:

```json
{
  "version": 1,
  "producer": "everytip-daily-tool",
  "feed_date": "2026-10-13",
  "upload_id": "daily-20261013-001",
  "generated_at": "2026-10-13T07:00:00Z",
  "source_sha256": "64 lowercase hex characters: SHA-256 of the exact CSV bytes"
}
```

`feed_date` is the **race date in Europe/London**, not the time of download or the WordPress post modification date. The importer checks the exact byte hash, schema, seven nonempty plain-text fields, time format, row limit, manifest identity, recent UTC generation timestamp and feed day. The default expected day is today in Europe/London; `--expected-date YYYY-MM-DD` supports a deliberately chosen future/pre-publication day. A stale or mismatched day fails closed. A hash only proves that CSV bytes match the supplied manifest; it does **not authenticate** who created both files. The operator and daily tool are the trust boundary until a signed or server-authenticated upload exists.

Run from `et-astro`:

```powershell
node scripts/import-daily-tips.mjs --manifest C:\path\daily.manifest.json --csv C:\path\daily.csv
```

The CLI writes one immutable `snapshot.json` under `artifacts/daily-tip-imports/uploads/<upload_id>/`. It reserves that upload ID before writing, writes to a temporary file, then atomically renames it; replaying the same ID fails without overwriting data. A different ID for the same race day is retained as a separate correction candidate and is **not automatically promoted**. Console output contains only local status, path, ID, day and row count, not selections. The artifact directory must remain Git-ignored because the JSON contains unpublished selections.

`tests/fixtures/daily-tip-import/` contains an obviously fictional one-row example. Do not treat it as actual picks. Tests cover successful intake, stale day/timestamp, changed CSV bytes, malformed rows, unsafe ID, future timestamp, duplicate ID and end-to-end local CLI output.

## Not yet connected

The current Ninja 72501 Google Sheet has no date column or reliable source-modified time, so downloading it today and attaching a newly minted manifest would **not** establish that the selections were prepared for today. The manifest must be generated by the existing daily tool when it creates the input file. The Kempton fixture table 86633 has a different schema and is excluded from this intake.

For **local exact-preview testing only**, set `EVERYTIP_DAILY_TIP_UPLOAD_ID` to a real validated upload ID when starting Astro with `MIGRATION_EXACT_PREVIEW=1`. `src/lib/opted-in-daily-tip-snapshot.mjs` reads that one ignored artifact and checks its identity, row shape, generated time and current Europe/London day. No environment variable, missing artifact, tampering or stale date produces no rows. Dark Horse and Kempton then use the approved `TipsTable` layout and mobile `+` details; Kempton filters only its own rows. The table is hidden in HTML by default and revealed by browser JavaScript only while the UK date matches, with a one-minute and tab-visibility recheck to close it at rollover. Without JavaScript, the unavailable message remains. No fictional fixture is automatically loaded on either exact page.

This does **not** make a static Astro build a live tips service: a validated local upload is not automatically delivered to Cloudflare, and the published Google Sheet still has no reliable date.
