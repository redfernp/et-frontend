# Local-only offer UID REST contract — 13 October 2026

The EveryTip Content Model plugin source now identifies as **0.7.0-dev**. It is **not uploaded or activated** on staging or live. The earlier v0.6 staging-upload question does not authorize this newer code; obtain a fresh, specific staging-only approval before deployment.

A staging-review ZIP has now been packaged locally at `artifacts/everytip-content-model-0.7.0-dev.zip` with SHA-256 `7BF710BE308435319167663EA53E1C08903BC4E8996515EAFB6FFDF5A6F43E21`. It contains the single `everytip-content-model/` plugin folder and seven source/assets files. Packaging is not deployment; the staging-only approval and PHP runtime checks below remain required.

The existing authenticated `GET /wp-json/everytip/v1/offer/{id}` is unchanged except for an additive `revision_token` derived from the complete returned state. The new authenticated `PATCH /wp-json/everytip/v1/offer/{id}/uid` accepts only:

```json
{"expected_revision":"<64 lowercase hexadecimal characters from GET>","uid":"quinnbet-welcome-001"}
```

The example UID is a **candidate naming pattern, not a selected permanent identifier**. The owner/editor must settle the permanent UID convention first. Request keys other than the two above, invalid formats or oversized UIDs are rejected. `edit_post` permission on the exact `et_offer` is required. Both WordPress status and editorial offer status must remain `draft`; an existing UID cannot be changed through this route. A stale state returns 409. A per-offer atomic edit lock serialises different-UID attempts against one blank record. The route scans all offer post statuses, including trashed records, for an existing UID, and makes a separate atomic WordPress option claim for a new UID before writing the single ACF field key. It retains that claim after success to prevent reuse. ACF readback and an append-only audit meta entry follow the write. It does not edit headline, short terms, eligibility, country, destination, CTA, publication status or other offer fields.

**Staging validation required before use:** PHP lint, route registration/permissions (anonymous 403, editor with exact `edit_post` allowed), wrong/missing revision 409/400, duplicate UID 409, retry with same UID idempotent, attempted replacement 409, and independent readback of the other offer fields and status. Simulate concurrent attempts if possible. A failed claim may require manual cleanup; do not blindly delete reservation options. A full authenticated offer-state backup is required before the first real UID write. No UID has been written by this local code change. The locks cover this REST route, not out-of-band WP-admin or other-plugin writes to ACF; no database-level uniqueness constraint exists. Treat any out-of-band UID edits as a concurrency/duplicate risk until independently audited.

**Recovery caveat:** the per-offer WordPress option lock is released by PHP `finally` on normal request completion, but a fatal process interruption can strand `_everytip_offer_uid_edit_lock_{id}` and cause later PATCH calls to return 409 indefinitely. There is no automatic stale-lock deletion in this untested version, because an unsafe TTL deletion could race an in-flight write. Before deploying, define an administrator-only inspection/recovery procedure that confirms no request is active and the full offer state is intact. The permanent `_everytip_offer_uid_claim_*` reservation must not be removed merely to clear an edit lock.

Local structural tests: `node --test tests/offer-uid-write-contract.test.mjs` (four passing as of 14 October). PHP CLI was not present on this workstation; these tests do **not** prove PHP runtime behaviour.
