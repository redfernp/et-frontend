# EveryTip WordPress to Astro Migration Spec

Date: 2026-07-10

## Purpose

Move EveryTip from a plugin-heavy WordPress implementation to an Astro build that preserves organic visibility, improves performance, and gives the editorial/SEO workflow a cleaner topical-authority model.

## Migration Principles

1. Preserve all indexable URL equity unless there is an explicit canonical consolidation decision.
2. Keep noindex/follow taxonomies and bridge pages intentionally noindex when the current SEO strategy depends on them.
3. Treat posts, evergreen pages, offer bridge pages, review pages, and author/column archives as different content types instead of flattening everything into one generic article model.
4. Keep WordPress as the CMS and publishing system. Astro should read WordPress at build time, not become the editorial source of truth.
5. Generate redirects from a single audited map, not from scattered config fragments.
6. Keep affiliate links and bookmaker outbound links behind a central link registry so `sponsored`, `nofollow`, UTM, and compliance attributes are consistent.
7. Validate SEO-critical output before launch: canonical, title, description, robots, schema, breadcrumbs, internal links, hreflang if added later, and XML sitemap membership.
8. Use WPGraphQL as the frontend data contract and REST API endpoints for backend tips/content automation, rebuild control, and scheduled jobs.

## Target Information Architecture

Recommended Astro content model:

| Collection | Purpose | Source |
| --- | --- | --- |
| `posts` | Time-stamped articles and tips currently in WordPress posts | WPGraphQL at build time, optionally via a generated snapshot if build volume demands it |
| `pages` | Evergreen landing pages, review pages, guides, and static pages | WPGraphQL pages and page metadata |
| `categories` | Indexable category hub metadata and intro copy | WPGraphQL categories, Yoast SEO fields, and SCN workbook decisions |
| `authors` | Expert/columnist profiles and author schema | WPGraphQL users/authors plus editorial metadata |
| `bookmakers` | Operator facts, offers, review ratings, compliance copy | WordPress fields or local registry, reviewed periodically |
| `racecourses` | Racecourse guide metadata and internal-link targets | WordPress page/post data and SCN workbook route policy |
| `redirects` | One row per legacy URL requiring redirect or keep-live decision | SCN/topical authority workbook export |
| `affiliateLinks` | Canonical outbound link definitions | WordPress/REST-backed registry or local data file, kept out of body copy where possible |

Recommended route handling:

- Preserve root-level legacy slugs such as `/betfred-review` and `.html` post URLs where possible.
- Preserve `/racecourses/{slug}` for racecourse guides unless a full redirect plan approves a new hierarchy.
- Keep bridge/offer pages such as `/bet365-sign-up-offer`, `/betfred-sign-up-offer`, and World Cup offer pages as noindex/follow unless the SEO/compliance owner changes that decision.
- Avoid creating duplicate routes for `slug` and `slug/` without a host-level trailing-slash policy.

## Astro Implementation Direction

Astro-specific decisions should follow the current official guidance:

- Use a typed frontend data layer around WPGraphQL so templates are not littered with raw GraphQL query details.
- Use Astro file-based routing for the public route shape, with dynamic routes for large content collections.
- Use configured redirects for explicit old-to-new URL movement, but handle trailing-slash normalization at the hosting layer because Astro redirects are not the right tool for that case.
- Store local migrated images in `src/` when Astro should optimize them; use `public/` only for assets that must be served as-is.
- For remote WordPress/CDN images during transition, authorize remote image sources in Astro config before using Astro image optimization.
- Keep the build fully static on Cloudflare Pages unless a specific runtime endpoint is needed. If runtime endpoints are needed for forms/tracking, isolate them in Pages Functions or Workers rather than making content pages SSR.
- Copy the Oddstips rebuild model: WordPress changes trigger a debounced Cloudflare Pages deploy hook, plus a scheduled fallback rebuild.

## WordPress Data And Rebuild Architecture

EveryTip should reuse the Oddstips separation of concerns:

| Lane | Tooling | Responsibility |
| --- | --- | --- |
| Frontend content | WPGraphQL | Posts, pages, categories, menus, Yoast SEO fields, author data, featured images, rendered content |
| Backend automation | WordPress REST API | Tip generation, content updates, offer updates, snapshot generation if used, rebuild triggers |
| Deployment | Cloudflare Pages deploy hook | Rebuild Astro after WordPress changes |
| Reliability fallback | Cloudways cron | Scheduled rebuilds and scheduled automation runs |

Initial recommendation:

- Start with WPGraphQL build-time queries because EveryTip's current footprint is moderate: 962 posts, 205 pages, and 8 categories.
- Batch GraphQL queries wherever possible. Avoid one network request per page if a paginated all-posts/all-pages query can feed `getStaticPaths`.
- Cache GraphQL responses in module-level build memory, as Oddstips does for menus.
- Add build health checks so a failed or partial WordPress response cannot deploy a thin broken site over the last healthy Cloudflare Pages build.
- If GraphQL build volume becomes slow or flaky, add an EveryTip snapshot endpoint that emits WPGraphQL-shaped JSON to `/wp-content/uploads/everytip-snapshot.json`, then have Astro fetch that once per build.

Recommended WordPress REST endpoints:

| Endpoint | Method | Purpose |
| --- | --- | --- |
| `/wp-json/everytip/v1/trigger-rebuild` | `POST` | Protected endpoint that calls the Cloudflare Pages deploy hook |
| `/wp-json/everytip/v1/generate-snapshot` | `POST` | Optional later endpoint to generate a build snapshot file |
| `/wp-json/everytip/v1/automation/tips` | `POST` | Backend tip/content automation entrypoint |
| `/wp-json/everytip/v1/offers/refresh` | `POST` | Offer review/update automation |

Protected endpoints should require a secret header, for example `X-EveryTip-Key: <secret>`, and should never expose Cloudflare deploy hook URLs in frontend code or public Git history.

Recommended rebuild triggers:

- On publish/update of an indexable post or page: enqueue a debounced rebuild.
- On category, author, menu, Yoast, ACF, offer, or affiliate-link update: enqueue a debounced rebuild.
- On bridge/offer page update: enqueue rebuild, but keep noindex/sitemap rules intact.
- Server cron fallback: trigger a rebuild on a predictable schedule, for example hourly during active content periods.
- Server cron fallback for automation: run backend tips/content jobs through REST or CLI, not visitor-triggered WP-Cron.

Debounce rule:

- Do not call the Cloudflare deploy hook on every `save_post` directly.
- Store a pending rebuild flag and run it after a short delay, for example 2 to 5 minutes.
- This avoids a burst of deploys when editing several fields, menus, or offers.

Hard build guardrails to copy from Oddstips:

- Add cache-busting to any snapshot fetch: `?cb=<timestamp>`.
- Use a browser-like User-Agent for build-time fetches if Cloudways or Imunify360 challenges bot-like requests.
- Fail the build if the fetched content count is suspiciously low.
- Fail the build if JSON/GraphQL parsing fails.
- Fail the build if too many expected canonical URLs are missing.
- Do not allow Astro to fall back to a tiny placeholder site and deploy successfully.

## Content Consolidation Rules

Use the SCN/topical authority workbook as the decision source.

| Case | Default action |
| --- | --- |
| Indexable evergreen page with traffic or links | Keep URL, migrate content, improve template |
| Indexable post with daily/dated value | Keep if it has search value; otherwise consolidate into hub and 301 |
| Noindex author/column archive | Recreate only if useful for internal discovery; keep noindex/follow |
| Duplicate bookmaker review variants | Pick canonical review URL, 301 alternates, document source |
| Bridge/sign-up offer page | Keep noindex/follow, preserve CTA attributes, do not add to XML sitemap unless approved |
| Thin tag/category archive | Noindex or remove; redirect only when there is a strong matching hub |
| `.html` post URL | Preserve if current canonical; otherwise map one-to-one to approved destination |

## SCN Strategy

SCN means Semantic Content Network for this migration: a mapped set of topic hubs, supporting articles, reviews, offers, and internal links designed to make topical authority visible to users and crawlers.

Initial topical pillars:

1. Horse racing tips
2. Football betting tips
3. Bookmaker reviews
4. Free bets and bookmaker offers
5. Betting guides and bet types
6. Racecourse betting guides
7. Sports betting by sport
8. Betfair exchange and profit guides
9. News and event-led betting coverage

Each pillar should have:

- One primary hub URL.
- Supporting cluster URLs grouped by sub-intent.
- A canonical money page or conversion path where relevant.
- At least three internal links from supporting pages back to the hub.
- Contextual links from the hub to the most commercially or editorially important supporting pages.
- Schema requirements defined at the template level.
- A clear update frequency.
- A content owner and QA owner.

## Schema Requirements

Minimum schema by page type:

| Page type | Schema |
| --- | --- |
| Homepage | `WebSite`, `Organization`, `SearchAction` if search remains |
| Article/tip | `Article` or `NewsArticle`, `BreadcrumbList`, author entity |
| Betting guide | `Article`, `FAQPage` where real FAQs exist, `BreadcrumbList` |
| Bookmaker review | `Review`, `Organization`, `FAQPage` only for visible FAQs, `BreadcrumbList` |
| Category hub | `CollectionPage`, `ItemList`, `BreadcrumbList` |
| Racecourse guide | `Article` or `Place` plus `BreadcrumbList`, depending on final template |
| Author profile | `ProfilePage`, `Person`, `BreadcrumbList` |

Schema must not advertise ratings, FAQs, offers, or authors that are not visible and auditable on the rendered page.

## Affiliate And Compliance Requirements

- Centralize bookmaker CTA generation.
- Apply `rel="nofollow sponsored"` on bookmaker outbound CTAs unless compliance/SEO explicitly approves a different policy.
- Keep affiliate redirect paths such as `/go/` blocked if they remain internal tracking routes.
- Do not expose affiliate IDs in editorial MDX where a registry entry can be used.
- Preserve age-gating and responsible gambling copy on bookmaker offer/review pages.
- Track every offer claim with last reviewed date, reviewer, jurisdiction, and source URL.
- Add an editorial review date field to high-risk YMYL/commercial pages.

## Technical Architecture

Recommended stack for the first implementation phase:

- Astro with TypeScript.
- Content collections for posts, pages, authors, categories, bookmakers, and racecourses.
- MDX only where the content needs components such as bookmaker tables, pros/cons, offer boxes, or calculators.
- Plain Markdown for straightforward informational content.
- One SEO component that owns title, description, canonical, robots, Open Graph, Twitter, and schema injection.
- One breadcrumb component fed by the route/content model.
- One affiliate CTA component fed by the bookmaker/link registry.
- A build-time sitemap generator filtered by index state.
- A redirects source file generated from the migration workbook.
- Playwright checks for template-level rendering and SEO assertions.

## Migration Phases

### Phase 1 - Inventory And Decisions

- Crawl all sitemap URLs.
- Export REST/WordPress data.
- Populate URL inventory and SCN workbook.
- Mark every URL as keep, improve, consolidate, noindex, remove, or redirect.
- Identify duplicate review and offer URLs.
- Approve route policy for `.html`, trailing slash, and `/racecourses/`.

### Phase 2 - Astro Foundation

- Scaffold Astro project.
- Add TypeScript, linting, formatting, testing, and build scripts.
- Define content collection schemas.
- Build shared layout, SEO, breadcrumb, article, category, bookmaker, offer, and author components.
- Add image and asset policy.

### Phase 3 - Data Transformation

- Export WordPress data.
- Convert HTML/blocks/shortcodes to Markdown or MDX.
- Normalize frontmatter.
- Download or authorize images.
- Generate content validation reports.
- Generate redirect candidates.

### Phase 4 - Template Buildout

- Implement homepage.
- Implement article/tip template.
- Implement evergreen page template.
- Implement category hub template.
- Implement bookmaker review and offer templates.
- Implement author/column template.
- Implement racecourse guide template.

### Phase 5 - SEO QA

- Compare legacy and Astro titles, descriptions, canonicals, robots, schema, headings, and rendered content.
- Validate XML sitemap output.
- Validate redirect map.
- Crawl Cloudflare preview for 404s, redirect chains, orphaned pages, and blocked assets.
- Run structured data checks on key templates.
- Confirm noindex pages are excluded from sitemap.

### Phase 6 - Launch

- Freeze WordPress publishing window.
- Run final export.
- Build Astro production artifact.
- Deploy Cloudflare preview/production candidate.
- Run full QA crawl against the preview and production candidate.
- Switch DNS/proxy/origin.
- Monitor logs, Search Console, analytics, affiliate click tracking, and redirect hit rates.

## Launch Go/No-Go Checklist

- All indexable legacy URLs either render at the same URL or 301 to an approved target.
- No known indexable URL returns 404, 500, or unintended noindex.
- XML sitemap contains only indexable canonical URLs.
- Robots file blocks only intended paths.
- Canonical tags are self-referential or intentionally consolidated.
- Redirect chains are below two hops; one hop is preferred.
- Affiliate CTAs render with correct destination, tracking, and `rel` attributes.
- Schema validates on representative templates.
- Core templates pass mobile layout QA.
- Production analytics and affiliate event tracking are verified.
- Editorial team has a publishing/update runbook.

## SCN Workbook Specification

The workbook should contain these tabs:

1. `Dashboard` - migration and topical-authority summary metrics.
2. `Sources` - sitemap, REST, docs, crawl, and manual-source references.
3. `Pillars` - one row per topical authority pillar.
4. `Clusters` - one row per cluster/supporting page idea.
5. `URL Inventory` - current WordPress URLs and migration decisions.
6. `Redirect Map` - old URL, new URL, status, reason, owner, QA status.
7. `Internal Links` - source URL, target URL, anchor, link purpose, status.
8. `Templates Schema` - page type, Astro template, schema, robots, sitemap inclusion.
9. `Backlog` - implementation tasks, owner, priority, dependencies, status.
10. `QA` - checks for redirects, metadata, schema, performance, links, and launch readiness.

Workbook formulas should calculate:

- Total URLs by action.
- Index/noindex counts.
- Priority score by URL.
- Pillar completeness by required cluster count and live cluster count.
- Redirect QA completion percentage.
- Backlog completion by phase.
- Internal link coverage per pillar.
